## Conditions carried into release

This gate passes **conditionally**. Three things are true of the deployment that
a reader should know before treating it as production-ready:

1. **Restore is untested (criterion 10).** Neon keeps history, and the schema can
   be rebuilt from migrations, but nobody has restored this database. The claim
   "we have backups" is currently a claim about Neon rather than about us.

2. **Performance is unmeasured (criterion 11).** NFR-001 names a figure and
   nothing has checked it. The index work was measured, which is not the same
   as measuring the deployed system under concurrent load.

3. **The free tier sleeps (RSK-007).** After fifteen minutes idle the first
   request takes 30 to 60 seconds. During a live demonstration this reads as a
   broken system to anyone watching. Mitigation is a keep-warm enabled for the
   defence window only (DEC-013), which is a demonstration measure, not an
   operational one.

Recording these as conditions rather than quietly passing the gate is the point.
A release gate that only ever passes is not a gate.

## Not in the release

Reservations exist and are tested but no frontend consumes them. Notification
delivery works for email; push is implemented and untested end to end, because
no device has registered against the deployment. Both are stated in the ledger
rather than implied by silence.
